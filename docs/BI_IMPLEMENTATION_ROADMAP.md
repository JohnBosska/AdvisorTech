# Tech Adviser — аудит и дорожная карта BI-платформы

Дата аудита: 13 ноября 2026. Источник требований: мастер-задание «Build an advanced AI-powered BI platform» (20 модулей, 6 фаз). Статус реализации по модулям ведётся в `BI_REQUIREMENTS_TRACEABILITY.md`, текущее состояние разработки — в `DEVELOPMENT_STATUS.md`.

## 3. Архитектурные слабости

1. **Нет хранилища.** BI-студия и AI считают всё по снимкам в браузере (до 5000 строк, 5 МБ). Это не масштабируется и блокирует семантический слой, финансовую аналитику, прогнозы и AI-SQL.
2. **Агент передаёт только счётчики.** Сквозной сценарий «подключил 1С → данные в облаке» не замкнут.
3. **Роли фиксированы enum-ом** из четырёх значений; прав на уровне объектов нет.
4. **Нет аудит-лога** действий пользователей и запросов ИИ.
5. **Temporal простаивает**: фоновых пайплайнов нет, хотя воркер развёрнут.
6. **Демо-страницы кабинета** создают ощущение готовности, которого нет; они помечены, но должны быть заменены витринами по мере появления данных.
7. **Расчёты в двух местах**: агрегации в браузере (`compute.ts`) и на сервере (`bi.py`). После появления хранилища расчёт должен уйти на сервер, браузер остаётся для снимков.

## 4. Сознательные отклонения от задания

- **pgvector вместо Qdrant** — решение владельца продукта в этой же работе; меняется одним провайдером в `app/resources/knowledge.py`, если понадобится.
- **Redis** не вводится, пока нет нагрузки, которую нельзя закрыть PostgreSQL и Temporal.
- **Anthropic** недоступен из региона прода (403), поэтому модели: GigaChat и DeepSeek.
- Интерфейс BI-студии — собственный, не копия Power BI.

## 5. Дорожная карта (сквозные инкременты)

### Фаза 1 — основа BI (текущая)
1. **Инкремент 1.1 — сырой слой хранилища** (сделано в этом коммите): агент передаёт записи, они сохраняются в `raw_records` с upsert по ключу, появляется API хранилища и источник «Хранилище» в BI-студии с кнопкой обновления.
2. 1.2 — аудит-лог действий и запросов ИИ (`audit_events`), выдача IT_ADMIN/OWNER.
3. 1.3 — фреймворк коннекторов: общий интерфейс `discover / schema / extract(incremental)`, серверные коннекторы PostgreSQL и MS SQL с хранением зашифрованных учётных данных (ключ из env), запуск через Temporal по расписанию, история запусков в `sync_runs`.
4. 1.4 — Connector Agent (отдельный пакет Python) для 1С на PostgreSQL / MS SQL в закрытой сети: чтение, батчи в `raw_records`.
5. 1.5 — правила качества данных (пустые ключи, дубли, типы) → `records_rejected/quarantined` с причинами.

### Фаза 2 — семантический слой и движок BI
6. Семантические модели: сущности, связи, измерения, иерархии, меры (формулы над SQL с белым списком функций), KPI-каталог с версиями.
7. Серверный запросный движок: семантический запрос → SQL с параметрами, RLS, лимиты, таймауты, кэш.
8. BI-студия на хранилище: визуалы запрашивают сервер; drill-down по иерархиям, drill-through к записям, сравнение периодов, условное форматирование, недостающие визуалы.
9. Экспорт на сервере (XLSX, PDF/PNG), расписания.

### Фаза 3 — бизнес-аналитика
10. Витрины продаж, запасов, закупок, логистики; шаблоны дашбордов.
11. Финансовая аналитика и РСБУ: план счетов, проводки, ОСВ, баланс и ОФР как аналитические представления; настройки учётной политики. Бюджеты и план/факт.

### Фаза 4 — AI на данных
12. AI-SQL строго через семантический слой (валидация, права, лимиты), объяснимость (источник, период, фильтры, метод), парсинг PDF/DOCX/XLSX, права на документы, переиндексация.
13. Генерация и правка дашбордов по тексту без разрушения существующих визуалов.

### Фаза 5 — продвинутая аналитика
14. Прогнозы с выбором модели и оценкой, аномалии, RCA по вкладу факторов, Health Score с настраиваемой методикой, сценарии, алерты и рекомендации.

### Фаза 6 — Decision Intelligence
15. Специализированные агенты и оркестратор, задачи и согласования, Embedded BI, коллаборация, варианты развёртывания.

## 7. Риски и зависимости

- **Доступ к 1С в закрытой сети** решается только агентом у клиента; до его появления работают OData/PostgreSQL с публичным адресом.
- **Объём данных на 2 ГБ VDS**: raw-слой в JSONB растёт быстро; нужны партиционирование и архив, затем ClickHouse при необходимости.
- **Качество LLM**: GigaChat нестабильно соблюдает схемы ответов, поэтому вся генерация SQL должна идти через семантический слой с валидацией, а не напрямую.
- **Отсутствие SMTP и DNS для `api.`** блокирует регистрацию пользователей и прямой API для агентов.
- Эмбеддинги зависят от баланса cloud.ru.
